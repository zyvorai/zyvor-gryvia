# Changelog

All notable changes to Gryvia are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project aims to follow [Semantic Versioning](https://semver.org/) once it leaves alpha.

## [Unreleased]

Entries are newest first within each section. Counts in an entry (for example "24 programs") are as of that entry; the
current numbers are 47 CRDs (43 with a registered controller) and 47 eBPF programs.

### Added
- Federation failover (opt-in `aiOperator.federation.failover`, ai-operator `--federation-failover`; needs `aiOperator.federation.allowedServers` and `aiOperator.kueueIntegration`): a `GryviaFederation` with `spec.failover.enabled` and `automatic` tracks each member's failure streak (`consecutiveFailures`, `unhealthySince`); after `healthCheck.failureThreshold` failures it fences the member (deletes its copies of the dispatched Jobs and Workloads through the validated kubeconfig, or, when unreachable, waits `spec.failover.leaseTimeout`, default 5m) and only then deactivates the manager's Kueue Workloads placed on it and reactivates them once Kueue has evicted them, so MultiKueue redispatches them. New fields `clusters[].multiKueueCluster`, `failover.leaseTimeout`, `status.clusterStatus[].fenced/fenceMethod/fencedAt`, `status.failovers[]`; condition `FailoverFenced`; Events. Chart values `aiOperator.federation.*` replace passing the federation flags through `extraArgs`. Checkpoints cross clusters through the existing replica module (`GRYVIA_CHECKPOINT_REPLICA=s3://...`; the elastic example image now includes boto3). Tested: ai-operator unit tests with fake manager and member clients, Helm render test `scripts/tests/federation-chart.test.sh`, and the kind e2e `e2e-multikueue.yml`, extended to three clusters (stop a worker, assert lease fencing, eviction, redispatch to the other worker and resume from an S3 replica on versitygw). Not tested: remote-delete fencing against a real outage, GPUs. See [federation failover](docs/federation-failover.md).
- Checkpoint guard and node-loss recovery (opt-in `aiOperator.checkpointGuard`, ai-operator `--checkpoint-guard`): `GryviaCheckpointGuard` no longer fakes checkpoints. A new batch training job with `spec.storage` matched by a guard gets `GRYVIA_CHECKPOINT_DIR`, `_EVERY` (new `checkpointPolicy.everySteps`), `_INTERVAL_SECONDS`, `_REPLICA` (new `replication.target`, `file:///` or `s3://`) and `_STATUS_CONFIGMAP`, plus a ConfigMap and a Role/RoleBinding letting its default service account get/update only that ConfigMap. The trainer reports commits there (`examples/training/checkpoint_status.py`, stdlib) and the operator copies them into the new `GryviaAIJob.status.checkpoint` and `GryviaCheckpointGuard.status.jobs`; `CheckpointValid` turns `Stale` after twice the interval; emergency triggers write a checkpoint request the trainer answers early. With `restore.autoRestore`, pods of a non-elastic job whose node is gone or NotReady for `restore.nodeLossGraceSeconds` (default 60) are force-deleted so the Job recreates them; `RecoveredFromNodeLoss`, `NodeLost` event and `lostSteps` are recorded. `examples/training/checkpoint_replica.py` replicates committed steps and restores them into an empty directory; `elastic_train.py` uses both. The fake periodic checkpoint and duration code is removed. Tested: ai-operator unit tests (matching, injection, RBAC objects, status sync, staleness, request de-duplication, node-loss grace and force deletion); `test_checkpoint_status.py` against a local fake API server and `test_checkpoint_replica.py`; `scripts/tests/checkpoint-guard-chart.test.sh`; a resumed local `torchrun` run matched an uninterrupted run's loss; the new kind job `e2e-elastic.yml` node-loss stops the node of a guarded non-elastic torchrun job after a reported commit and checks replacement, resume from the committed step and completion (runs in CI, not run locally). Not run on GPUs, cloud node failures or S3.
- DCP checkpoints with optimizer resharding: `examples/training/dcp_checkpoint.py` saves model and optimizer state with `torch.distributed.checkpoint` (`get_state_dict`/`set_state_dict`, so plain, DDP and FSDP2 models) under `steps/<S>/dcp/` and commits the step through the existing COMMIT/COMMITTED protocol (`format: dcp`, saving world size, sha256 of every DCP file); `load` verifies the files on rank 0 and reshards to the current world size. `checkpoint_contract.verify_committed` verifies DCP checkpoints and reports `optimizerReshardable: true` only for them. `elastic_train.py` now trains with DDP and Adam and checkpoints through DCP (older blob checkpoints are still resumed), and its `DONE` adds `resumedFromWorld`. Tested: `test_dcp_checkpoint.py` spawns gloo processes on CPU, saves at world size 4 and loads at 2 and 3 with DDP and with FSDP2 (every parameter, Adam moment and step counter compared, ranks consistent after another step, half-written step ignored, corrupted shard rejected); `test_checkpoint_contract.py` covers DCP records (stray file, checksum, path traversal, unknown format); the new `repo-checks.yml` job runs these with CPU torch 2.8.0 and resumes `elastic_train.py` under `torchrun` from world size 4 at 2. Not run on GPUs or with NCCL.
- Dataset pool placement: `GryviaDataset.spec.placement.pools[]` keeps a verified copy of the current version per node pool (PVC `dataset-<name>-<pool>` filled by a pool-pinned download Job, digest compared with the primary copy, `status.replicas[]`, condition `Placed`, removed pools pruned); `cache.warmup` now starts those downloads with the primary. A `GryviaAIJob` annotated `gryvia.io/dataset: <name>` ranks nodes in pools with a verified replica first, gets soft node affinity toward them and mounts the replica read-only at `/datasets/<name>` when it runs in the dataset's namespace on one node (or the replica is ReadOnlyMany/ReadWriteMany); the decision is in `status.dataset`. Unit-tested with fake clients in both operators; not run on a multi-node cluster.
- Submit-time preflight: a `GryviaAIJob` annotated with `gryvia.io/model-params-billions` (optional `weight-bits`, `tensor-parallel`, `extra-memory-gib`, `require-fast-interconnect`) is checked against pools built from the cluster's GPU nodes (GPU type, node shape, estimated memory per GPU from `gryvia.io/gpu-memory`, RDMA, interconnect). The webhook denies malformed annotations and warns when no pool fits; opt-in `aiOperator.preflightEnforce` (`--preflight-enforce`) rejects such Pending jobs with reason `PreflightBlocked`, failing open on lookup errors, empty clusters and unknown memory. The Go port (`pkg/preflight`) and the gateway engine share golden cases tested on both sides. Unit-tested with fake clients; not run on GPU nodes.
- Operation record lifecycle: `GET /api/intelligence/actions` is paged (`limit` up to 500, `continue` token), `GET /api/intelligence/actions/export` returns up to 10,000 records, and finished records (Rejected, Applied, RolledBack, expired proposals) older than `apiGateway.intelligenceRetentionDays` (default 30, `0` keeps all) are deleted hourly per replica or on `POST /api/intelligence/actions/sweep`, with a resourceVersion precondition. Records of uncertain writes (Executing, RollingBack) are never deleted. The intelligence Role gains `delete` on ConfigMaps in the gateway namespace. Unit-tested against a fake ConfigMap store; Helm render test updated.
- Workload intelligence: typed analysis APIs and a dashboard workbench for preflight, training evidence, useful-work cost, serving SLO recommendations, benchmark comparison, checkpoint compatibility, dataset locality, fabric qualification, capacity simulation and residency-aware fleet planning. Live job evidence and usage joins retain namespace/marking filtering and job UID attribution. Includes a framework timing adapter, immutable SHA256 file cache, all-rank checkpoint contract verifier and executable streaming model benchmark. Opt-in `apiGateway.intelligenceActions` adds durable ConfigMap proposals, separate named OIDC review, target UID/resourceVersion preconditions, execution and rollback for inference replicas, quota limits and node cordon; the copilot can propose only. Gateway/API, SDK, benchmark/checkpoint and dashboard tests pass; Helm opt-in/off renders and lint checked. No real GPU/RDMA/model-server validation, continuous SLO controller, optimizer resharding or new cross-cluster dispatch/failover is claimed. See [workload intelligence](docs/workload-intelligence.md).

Each entry shows freshness (newest version time) and what is downstream of it (jobs mounting its volume, then models and services, from the lineage graph). Unit-tested; no connectors yet (datasets still come from http, s3 or nfs sources).

- LLM gateway activator for scale-to-zero services: a request for a `ScaledToZero` model sets `gryvia.io/wake-requested` and is held until the service is ready (503 with `Retry-After: 30` after `coldStartTimeoutSeconds`), then proxied and metered; proxied requests write `gryvia.io/last-request`, at most once a minute per service. - `GryviaInferenceService.spec.scaleToZero` (`enabled`, `idleSeconds`, `coldStartTimeoutSeconds`): the controller scales an idle service's Deployment to 0 replicas (phase `ScaledToZero`, condition `ScaleToZero`, `status.scaledToZeroAt`) and back to `max(1, minReplicas)` when the `gryvia.io/wake-requested` annotation appears, which it then removes ([docs/inference-serving.md](docs/inference-serving.md#scale-to-zero)). Idle time counts from the gateway's `gryvia.io/last-request` annotation or the last wake-up; a service that is not ready yet gets the cold-start time on top. The HPA is left alone at zero. Not applied while a canary is enabled.
- Real Slurm on Kubernetes (opt-in): SchedMD's Slinky slurm-operator as a sub-chart (`slurmOperator.enabled`, 1.2.3) and a Slurm 26.05 cluster templated by the chart (`slurm.enabled`: slurmctld, slurmrestd, keys). With `quotaOperator.slurmIntegration` the quota operator gives every GryviaTenant a NodeSet and partition `gryvia-<tenant>` (nodes from the GPU quota) and writes each finished job in those partitions as a `GryviaUsageRecord` of the new kind `slurm`, so budgets and chargeback include Slurm. Kind e2e: `.github/workflows/e2e-slurm.yml` ([docs/slurm.md](docs/slurm.md#real-slurm-slinky)).
- `gryvia submit --sbatch script.sh [--image IMAGE] [--dry-run]` imports Slurm batch scripts ([docs/slurm.md](docs/slurm.md)). `#SBATCH` directives map to `GryviaAIJob` fields: `--nodes` (a range makes an elastic job), `--ntasks`, `--gres=gpu[:type]:N`, `--gpus*`, `--cpus-per-*`, `--mem*`, `--time`, `--partition` (the Kueue queue), `--chdir`, pyxis `--container-image`, and `--array` (one job per index). The script runs with its own interpreter; `SLURM_PROCID`, `SLURM_NTASKS`, `SLURM_JOB_ID`, `SLURM_ARRAY_*` and others are set per pod, `srun` runs its command once per pod and `scontrol show hostnames` returns pod 0. Other directives warn and are ignored. `scripts/e2e-jobs.sh sbatch` runs a 2-node script and a 2-index array through the CLI on kind. The FAQ no longer says there is no importer.
- Elastic training with a replicated rendezvous ([docs/elastic-training.md](docs/elastic-training.md#a-replicated-rendezvous-etcd)). torch's `etcd-v2` backend works against a 3-member etcd 3.5 cluster with `--enable-v2`; `python-etcd` is now in the elastic image. `e2e-elastic.yml` gains a third case: one etcd member is removed (quorum kept), then index 0's node is lost, and the survivor must re-form through the remaining members and finish alone.
- `e2e-kueue.yml` checks a checkpoint on Kueue preemption (`scripts/e2e-kueue.sh preempt-checkpoint`). A 2-worker job with `gryvia.io/checkpoint-command` and `retryLimit: 0` is preempted by a higher-priority job; its trainer saves only when the preStop hook asks; after readmission both workers resume from that step and the job Succeeds, so an eviction does not consume `retryLimit`. `docs/kueue-integration.md` no longer says nothing checkpoints first.
- The Kueue e2e runs the elastic trainer under partial admission (`scripts/e2e-kueue.sh elastic-torchrun`). A real `torchrun` job asks for 4 workers (`minNodes: 2`) against 2 slots of quota. Kueue admits 2, torchrun forms a group of 2, and training finishes all 20 steps with every checkpoint committed by both ranks.
- Model factory: lm-eval runs through a serving endpoint. The kind e2e scores the llama.cpp-served fine-tune on `gsm8k` (8 questions) next to the facts, and checks that `live_score` is their mean. `evaluate.py --tokenizer` names the Hugging Face tokenizer lm-eval needs for `--endpoint --tasks`; it defaults to the served model name, which is usually not a hub ID. The images install `lm-eval[api]`: without the extra, `--endpoint --tasks` failed (`tenacity` missing). Multiple-choice tasks through an endpoint need prompt logprobs, which llama.cpp's server does not return; the docs say so.
- The kind e2e runs the model watch against the real Hugging Face API (read-only, no token): a baseline of HuggingFaceTB's SmolLM2 base models with the hub's revisions, license and safetensors sizes, then a watch with `includeExisting` that rejects SmolLM2-1.7B by `maxParamsB` and runs a workflow for SmolLM2-135M with the hub's revision.
- `examples/model-factory/convert_gguf.py`: llama.cpp's converter on a merged model, writing `model-<outtype>.gguf` next to the safetensors (outputs `path`, `subPath`, `file`, `format: gguf`, `bytes`); `Dockerfile.cpu` carries the converter and gguf-py from llama.cpp b11347. The kind e2e converts the fine-tuned model, registers the GGUF directory, serves it with llama.cpp from the registry PVC through a `GryviaInferenceService` with `modelRef`, scores it through the endpoint and writes `live_score` onto the entry with a registry step.
- Elastic training survives losing index 0 ([docs/elastic-training.md](docs/elastic-training.md#losing-index-0)). `examples/training/rendezvous_store.py` (in the elastic image) is a standalone c10d rendezvous store; the torchrun agents use it with `--rdzv_conf=is_host=0`. The operator sets `TORCH_DISABLE_SHARE_RDZV_TCP_STORE=1` on elastic jobs: otherwise torch 2.8 fails an assertion when another node becomes rank 0. `e2e-elastic.yml` is now a matrix that loses index 1 in one run and index 0 in the other; when index 0 is lost, the survivor must finish as `rank 0 of 1`.
- Elastic AIJobs under Kueue are partially admitted ([docs/elastic-training.md](docs/elastic-training.md#under-kueue)). The batch Job gets `kueue.x-k8s.io/job-min-parallelism: <minNodes>` and `kueue.x-k8s.io/job-completions-equal-parallelism: "true"`, so a short quota admits between `minNodes` and `nodes` workers instead of queueing the job; the Ready condition counts the admitted workers. `e2e-kueue.yml` gains an `elastic` step on kind. A 4-worker job against 2 slots runs with 2 workers. A 2-worker job with `minNodes: 1` completes through its success policy while index 1 is still running, its Workload is Finished and the quota is released.
- The model factory e2e runs lm-evaluation-harness for real: both evaluation steps score 20 `arc_easy` questions on CPU next to the made-up facts (`lm-eval==0.4.13` in `examples/model-factory/Dockerfile.cpu`). The step checks the per-task outputs, that the score is their mean, and that the fine-tune loses at most 0.25 on `arc_easy`.
- The model factory scripts run for real in the kind e2e: a `GryviaWorkflow` of AIJob steps downloads SmolLM2-135M from huggingface.co at a pinned revision, scores it on eight made-up facts, LoRA fine-tunes it on CPU, scores the merged model and registers it with both scores; the step requires the score to rise from at most 0.25 to at least 0.875 (5 epochs; with 3 the score moved between 0.5 and 0.875 across nearby learning rates). New `examples/model-factory/Dockerfile.cpu` (CPU torch, pinned TRL/PEFT/transformers) for those steps.
- Datasets: `source.s3.endpoint` points an s3 dataset at any S3-compatible service (MinIO, Ceph RGW, R2, ...), passed to the AWS CLI as `AWS_ENDPOINT_URL`; also accepted by `POST /api/datasets`. The kind e2e now runs the s3 path with the real AWS CLI image against versitygw: a first version, then an incremental one after objects changed, were deleted and were added (unchanged objects stay hard-linked to the old version, which is untouched).
- A real model engine in the kind e2e: llama.cpp's server (`ghcr.io/ggml-org/llama.cpp:server-b11347`, CPU) serves Qwen2.5-0.5B Instruct (Q4_K_M) as a `GryviaInferenceService` behind the LLM gateway. The new step checks a real completion and its usage, a streamed answer with the usage chunk, metering, and an agent whose model really decides to call its HTTP tool and answers from the result, non-streamed and streamed. No code change; the stand-in models stay for the deterministic assertions.
- Datasets: the nfs source runs in the kind e2e. A kernel NFS server on the runner exports a directory, the kind node gets the NFS client, and the download Job mounts the export and copies it (nested files, a second version after the export changed, retention).
- Elastic training across nodes in a new kind e2e (`e2e-elastic.yml`, `scripts/kind-elastic.yaml`): two `torchrun` workers on two tainted kind nodes (required anti-affinity) checkpoint to a ReadWriteMany NFS volume exported by the runner; after a commit with world size 2 the node of worker 1 is stopped and deleted, the replacement pod stays Pending, and the survivor must re-form the group alone, resume from the committed step and finish, completing the Job through its success policy. `docs/elastic-training.md` documents the NFS mount options the commit protocol needs (`noac`, `lookupcache=none`).
- Datasets resume and sync incrementally ([docs/datasets.md](docs/datasets.md#what-the-controller-does)): a failed download leaves its temporary directory (tagged with the source hash) so the Job's retry continues it: http with `wget -c` (falling back to a fresh download), s3 fetching only what is missing. A new s3 version starts as hard links to the current one and `aws s3 sync --delete` downloads only new and changed objects. The Job gets `HASH` and `CURRENT`. Checked under busybox with a Range-capable stand-in and a fake `aws`; not run against S3.
- Job hooks deliver from a worker pool ([docs/job-hooks.md](docs/job-hooks.md#delivery)): the job reconcilers only queue due deliveries; `--job-hook-workers` (`aiOperator.jobHooks.workers`, default 8) goroutines POST them, record the outcome on the job with a conflict-retried update, and enqueue the job again. A slow receiver no longer holds a reconcile for every hook of a job in turn; a full queue (256) retries the job after a second. Delivery stays at least once.
- Elastic training runs on kind ([docs/elastic-training.md](docs/elastic-training.md#reference-trainer)): `examples/training/elastic_train.py` (image `examples/training/Dockerfile.elastic`, CPU torch) is a data-parallel trainer for `torchrun` with coordinated checkpoints, a short collective timeout (`COLLECTIVE_TIMEOUT`) so a lost peer fails fast, and resume with another world size. `coordinated_checkpoint.py` gains `load_replicated` (rank 0's blob of the committed step, checked against COMMIT) and `discard_uncommitted` (drops half-written steps before a restart). The kind e2e runs it as an elastic AIJob (`nodes: 2`, `minNodes: 1`, gloo), deletes worker index 1 after step 10 is committed and expects a resume from a committed step, all 60 steps trained and the AIJob Succeeded. Not run on GPUs or with NCCL.
- Agents stream ([docs/agents.md](docs/agents.md#streaming)): the agent runtime accepts `"stream": true` (it returned 400 before). It streams each model call from the LLM gateway, relays the text as `chat.completion.chunk` server-sent events, assembles tool calls from their deltas, sends one extra event per tool call it runs, and ends with an event carrying the summed `usage` and the `gryvia` block, then `[DONE]`. A gateway error before the first event keeps its HTTP status; after it, the error is an event. `POST /api/agents/{name}/chat` takes `"stream": true` and relays the events. The kind e2e streams a tool-using chat through the api-gateway.
- LLM gateway: `tokensPerDay` is shared across replicas ([docs/llm-gateway.md](docs/llm-gateway.md#quotas)). Today's counts live in a ConfigMap per UTC day (`gryvia-llm-tokens-<date>`, release namespace); every `--quota-sync-interval` (`llmGateway.quotaSyncInterval`, default 1s) each replica adds its counts with an optimistic-concurrency update and reads back the totals. A replica sees the others' traffic within about two intervals, instead of only as of a once-a-day read of the usage records. The first replica of the day seeds the counter from that day's records; counters older than yesterday are deleted. The chart adds `POD_NAMESPACE` and a Role for ConfigMaps in the release namespace. The kind e2e runs two gateway replicas and expects a 429 from each.
- Job hooks (opt-in: `aiOperator.jobHooks.enabled`, `--enable-job-hooks`; see [docs/job-hooks.md](docs/job-hooks.md)): `GryviaJobHook` is rebuilt as a namespaced kind (`gjh`) with a controller. When a `GryviaAIJob` or `GryviaWorkflow` in the hook's namespace reaches one of its events (`Running`, `Succeeded`, `Failed`, `Cancelled`, `Preempted`, `Rejected`), filtered by kind and label selector, the ai-operator POSTs a JSON body (or a Slack `{"text"}` message), signed with HMAC-SHA256 like the budget webhook when `secretRef` is set, with `X-Gryvia-Event` and a stable `X-Gryvia-Delivery` id. - `GryviaGPUSharingPolicy` did nothing: its reconciler existed but was never registered in the GPU operator, so the NVIDIA one-click time-slicing and MIG labels were never written (the earlier NVIDIA one-click entry said otherwise). It is now registered behind `--enable-gpu-sharing` (chart `gpuOperator.gpuSharing`, off by default because it writes node labels) and has unit tests that check the labels on the nodes. The platform-completion change that removed this controller as a dormant legacy one now keeps it.
- `scripts/deploy-remote.sh` no longer fails with `GRYVIA_NETRA_URL: unbound variable` when the Netra flags are unset, and no longer exits silently after "Installing CRDs ..." (its CRD version check matched only one of the two YAML layouts in `crds/`).
- The release rehearsal showed the eBPF collector image has never built (its kernel programs do not compile). It is no longer published and is off by default in the network-intelligence chart; documented as experimental. (The image builds again since the CO-RE port listed under Added, but it is still not published.)
- Costs are labelled as spend to date; empty states name the operator or collector that feeds the data instead
  of showing reassuring zeros.
- Rate limits count per client address instead of per proxy pod.

### Security
- Seven code-scanning alerts closed: the gateway's session signing key is derived with PBKDF2-HMAC-SHA256 (200,000 iterations, cached) instead of a bare SHA-256, so sessions issued before the upgrade stop validating once; the GPU-count node label is parsed with a 32-bit `ParseInt`; the test TLS server requires TLS 1.2 or newer; `ebpf.yml` and `k3s-bootstrap.yml` run with read-only `contents` permission.
- A finished `GryviaUsageRecord` can no longer be edited through the API (see Added); deleting and recreating one is not blocked.
- Dashboard sessions are signed, expiring tokens issued by `/api/auth/login`; the API key is no longer stored in the browser.
- The dashboard bundle no longer contains a login credential; the gateway validates sign-in.
- The chart runs no root containers: the TLS Secret is mounted with `fsGroup` instead of a root init container.
- Login attempts are constant-time compared, delayed on failure and rate limited per client address.
